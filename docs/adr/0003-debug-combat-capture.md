# Debug combat capture and evidence pipeline

Status: accepted; live acquisition amended on 11 November 2026.

Aetheris provides a debug-only combat analysis page backed by one packet-ingestion contract shared by an offline PCAPNG adapter and a live Windows adapter. The offline adapter must be validated against the supplied captures before live capture is connected to the same parser and TCP reassembly pipeline. Network analysis is implemented in Rust without Npcap or a third-party packet-analysis library. Live acquisition uses native Winsock in the privileged `AetherisCapture` Windows service; Aetheris itself runs as a standard user. The service filters connections by the AION 2 process and sends original packets to the same user-side parser and TCP reassembly pipeline as file imports. This keeps evidence and analysis comparable while accepting the maintenance cost of a custom parser and a privileged Windows acquisition component. Installation and service coordination follow [ADR 0007](0007-windows-installer-and-update-service.md).

## Considered options

- Use Npcap or another packet-analysis library for live capture and protocol parsing. Rejected because the project requires no external network-analysis library and no Npcap.
- Elevate the application for every capture, or ask players to create firewall rules manually. Rejected because normal use must stay unprivileged and acquisition should support long-running use. The installer configures the service and its executable-scoped inbound TCP permission once.
- Require the game and Aetheris to have the same Windows account. Rejected because UAC can launch the game using a separate administrator account within the same interactive session; that restriction prevented game detection for standard-user players.
- Implement separate file and live decoding pipelines. Rejected because their results and error behavior could diverge; both adapters instead supply original packet bytes and capture metadata to the same analysis pipeline.

## Consequences

- PCAPNG import retains packet bytes, timestamps, interface/link metadata, source name, and file fingerprint in SQLite at `%LOCALAPPDATA%\Aetheris\debug-captures.sqlite3`; it does not duplicate the complete source file. Corrupt input may produce a partial session, and parsing stops when the next block boundary cannot be trusted.
- Sessions retain raw packets, reconstructed application messages, and zero or more decoded sections until explicit, confirmed deletion. Reanalysis replaces interpretations only after a complete successful run; raw evidence remains unchanged.
- Stopped sessions can be exported through “Exporter en PCAPNG”, including imported or partial sessions. Export streams every stored raw packet independently of UI filters and decoding, preserving order, packet bytes, captured/original lengths, link types, and available timestamps (including original resolution and offset). Interfaces are renumbered within each section; untimed packets use isolated Simple Packet Blocks, without inventing timestamps. The output follows the [PCAPNG block definitions](https://www.ietf.org/archive/id/draft-tuexen-opsawg-pcapng-05.html#section-4). This reconstructs a capture from stored evidence, not the original imported container: unretained options, names, and Aetheris interpretations are not exported. An export failure leaves an existing destination intact.
- By default, the analyzer fails closed for incomplete or ambiguous streams. A mid-connection start may now be recognized automatically from three coherent server ticks on valid message boundaries, as authorized on 3 November 2026. The inferred synchronization is recorded; bytes preceding it remain raw. TCP gaps or conflicting overlaps, truncated packets, unsupported link/network forms, and fragmented IP traffic remain visible as raw evidence without automatic resynchronization after the error.
- The live adapter waits for AION 2 connections in the authenticated application’s Windows session, follows a relaunch when exactly one game process is present, and reports ambiguity instead of selecting among multiple matching processes. The game may belong to a different account, including an administrator supplied at the UAC prompt. Other Windows sessions remain excluded, and UDP endpoints shared with other processes are not attributed to the game. Interface selection is inferred from the client socket when possible, with manual selection as fallback; permission failures do not trigger automatic elevation.
- Live capture requires the protected installer-managed installation. The client and service authenticate each other through Windows-owned loopback TCP endpoints; the service also checks the installed client executable. The client supplies no trusted PID or personal database path. Packet storage and interpretation stay in the application’s user profile, outside the privileged service.
- Offline packet import remains available independently of the Windows-only live adapter, including in manual ZIP installations. The debug page is excluded from production builds; service acquisition code remains available in production builds. Automatic service startup provides availability, not unattended recording: Start/Stop still controls acquisition, and continuous recording with the interface closed remains future work. Existing in-memory debug analysis is not yet suitable for unlimited retention.
- Live capture is limited to IPv4 in this version. Winsock raw IPv6 reception does not provide the original IPv6 header, so it cannot satisfy the original-packet contract; IPv6 remains supported for offline analysis. See [Microsoft raw-socket receive rules](https://learn.microsoft.com/en-us/windows/win32/winsock/tcp-ip-raw-sockets-2).
- Forced midstream alignment remains an explicit, persisted offline-only fallback when automatic synchronization finds no supported boundary. It assumes a message boundary at the first reconstructed captured byte and is labelled as an experiment. Both supplied PCAPNG files lack SYN packets but now synchronize through repeated server ticks without this option. See the [implementation report](../protocol-decoding.md#état-de-limplémentation) for the recognition limits and outstanding validation.
- Compressed messages retain their enclosing envelopes and source packets under [ADR 0006](0006-compressed-message-provenance.md). Recognizing a documented opcode is distinct from decoding its body; unknown or uninterpreted content remains available as raw bytes.
- rusqlite supplies SQLite storage, sha2 supplies source fingerprints, and windows-sys supplies native Windows declarations. None of these dependencies performs packet capture analysis, protocol parsing, or TCP reassembly.

## Validation limits

Native Windows tests cover authenticated IPC endpoint ownership, refusal of a foreign executable, bounded requests and original-packet transport. Game discovery is exercised with real test processes and a simulated different client SID in the same session; other sessions and ambiguous game processes remain excluded. These tests do not establish end-to-end packet reception from an actual game launched with separate administrator credentials. That scenario, both traffic directions, service restarts and sustained capture remain part of the system checks in [the installer guide](../windows-installer.md#validation-de-la-capture-par-service).
