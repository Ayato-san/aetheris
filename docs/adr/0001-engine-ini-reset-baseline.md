# Engine.ini reset baseline

The baseline location decision is superseded by
[ADR 0007](0007-windows-installer-and-update-service.md) for installer-managed
Windows installations. The original baseline semantics below remain applicable.

Aetheris keeps beside its executable an original-state reference containing only `[Core.System]` game-content paths and the `[/Script/Engine.RendererSettings]` DLSS/FSR values supplied by the player. The bundled content paths come from the local Aion 2 configuration and are retained for reference only; they are never used to restore or rewrite the player’s paths. Renderer defaults come from the explicitly supplied original block, never from the current customized file. Values already customized in the player's file are treated as custom, not as the origin baseline. Returning a category to its original state leaves paths untouched, restores the renderer settings from the clean reference (`r.ngx.dlss.enable=1` and `r.fidelityfx.fsr.enabled=0`), and removes that category's managed properties absent from the base file, including custom values that were present before Aetheris initialized; this avoids a full-file restore that could overwrite unrelated content. When changing the DLSS/FSR profile, Aetheris changes only those two properties and preserves other renderer settings. An absent or unrecognized value for any managed setting remains untouched until the player explicitly chooses a value or applies the recommended settings for its category. The recommended profile is selected from confirmed GPU and game compatibility, falling back to Off if none is confirmed; a manually corrected GPU selection persists across Aetheris launches. Per-setting reset controls remain available. Category-level reset removes only managed properties in the selected logical category that are absent from the base file, or restores that category's baseline values; it preserves other categories and unknown keys, even when they share a physical INI section. Category-level recommended apply likewise changes only the selected category and may overwrite that category's custom values. The global “Tout appliquer” and “Tout réinitialiser” actions apply the recommended profile or reset all 13 categories in one atomic file write. Successful global actions replace pending drafts; a validation or write failure preserves both the drafts and the file without partial application. `[Core.System]` paths remain untouched.

Whenever Aetheris writes managed settings for a logical category, it places a recognizable INI comment immediately above that category's contiguous key block, formatted `; Aetheris — <category name>` (including the category number and name). Categories sharing a physical INI section remain in separate, individually labeled blocks, separated by exactly one blank line. Repeated edits and resets do not accumulate separators. Category reset removes only that category's managed keys and marker, while preserving other category blocks, unknown keys, and user comments. A per-setting reset removes the marker if it leaves that category with no managed keys; otherwise the marker remains. Baseline values restored by a category reset do not retain that category's Aetheris marker. The original renderer block is restored immediately below its header using the lowercase key names above, without surplus blank lines. A reset removes section headers whose bodies become empty or whitespace-only, while retaining sections containing user comments, unknown content, or another category’s settings.

Numeric fields reject text at entry, paste, and composition time; they accept the sign and decimal separators appropriate to each setting. Incomplete numeric drafts remain editable but cannot be saved. Each content change restarts a two-second inactivity timer. Only modified logical settings are saved, with linked values validated together; unrelated drafts and focus are preserved. Choice controls and switches save immediately. Closing the window attempts to save pending drafts immediately; validation or write failure keeps the window open with the error visible. The UI displays confirmation only after a successful save, without announcing the timer or the file-protection mechanism. The page header keeps save confirmation and validation errors visible while the category list scrolls.

After every successful save, including an unchanged-value save, Engine.ini is made read-only on disk. Aetheris temporarily obtains write access for its next atomic replacement and reapplies the protection after success; a failed write restores the previous permissions. This file attribute is separate from the editing lock while the game runs described in ADR 0002. Old generated references with DLSS at 0 or missing content paths are migrated to the corrected reference; unrelated settings in a reference never become reset defaults.

Player-facing option descriptions and any generated per-option comments in `Engine.ini` explain the setting and its intended effect directly, using concise language and avoiding caveats such as “Aion 2 may not support this feature.” Keep compatibility uncertainties and source limitations in this internal ADR only; do not show or write them to the player's UI or INI. Community-provided settings are presented according to their supplied intended function.

For `[/Script/Engine.InputSettings]`, the four managed properties are absent from the clean baseline. Their recommended values are `InitialButtonRepeatDelay=0.001`, `ButtonRepeatDelay=0.001`, `bEnableMouseSmoothing=False`, and `bCaptureMouseOnLaunch=True`. Delay fields are entered in milliseconds, accept positive decimal values from 1 ms with no configured maximum, and are converted to seconds for the INI; comma and period decimal separators are accepted in the UI, with a period written to the file. Existing values below 1 ms or otherwise unrecognized are preserved until the player explicitly changes them or applies recommended settings. The input descriptions explain behavior without promising reduced stutter.

For `[/Script/Engine.Engine]`, the four managed properties are absent from the clean baseline. Their recommended values are `bUseVSync=False`, `bSmoothFrameRate=False`, `MinSmoothedFrameRate=5`, and `MaxSmoothedFrameRate=360`. The frame-rate limits are entered as positive FPS numbers, with no configured upper bound and with Min ≤ Max enforced; they remain editable while smoothing is off, with the UI indicating they are not expected to apply in that state.

For `[SystemSettings]`, `FullscreenMode`, `PreferredFullscreenMode`, and `r.SetRes` are absent from the clean baseline and are managed together by one three-state display-mode control. Its states are Windowed (`FullscreenMode=2`, `PreferredFullscreenMode=1`, `r.SetRes` suffix `w`), Borderless (`1`, `1`, suffix `wf`), and FullScreen (`0`, `0`, suffix `f`). The recommended mode is Borderless. The recommended resolution is the native pixel dimensions of Aion 2's display (the display’s preferred mode, accounting for portrait rotation, rather than its current desktop resolution); Aetheris identifies the game window's monitor when possible and falls back to the primary monitor. If a window overlaps multiple monitors, the monitor with the largest overlap is used. Width and height form one setting, are positive integer pixel inputs without an arbitrary upper limit, and changing a single dimension forms the complete pair using the other suggested/current value. A suggestion is refreshed when the display changes or the page opens, without overwriting a custom value or writing the INI. Values above the detected native resolution are accepted with a warning. The mode suffix is derived from the selected display mode.

The shadow properties added under `[SystemSettings]` are absent from the clean baseline. Their recommended values are `r.ShadowQuality=1`, `r.Shadow.MaxResolution=256`, `r.Shadow.CSM.MaxCascades=1`, `r.Shadow.CSM.TransitionScale=0.2`, `r.Shadow.DistanceScale=0.2`, `r.Shadow.MinResolution=62`, `r.DistanceFieldShadowing=0`, `r.ContactShadows=0`, `r.AOQuality=0`, and `r.Shadow.FilterMethod=1`. Boolean properties use switches; `r.AOQuality` uses Off/Moyen/Élevé states (`0/1/2`); integer-valued properties use integer fields and scale properties use decimal fields, without arbitrary limits where a supported range is not established. A clear warning about the profile's substantial shadow-quality reduction is visible before applying it, without a confirmation modal. Player-facing explanations distinguish disabling distance-field shadowing or distance-field AO from disabling all shadows or all ambient occlusion, and describe the intended filtering effect of `r.Shadow.FilterMethod`. Any version-specific caveat is internal only.

The character-visibility properties `g.OptimizeChar.ServerVisible.MinLength` and `g.OptimizeChar.ServerVisible.Length` are also absent from the clean baseline and are community-reported Aion 2 settings. Their recommended values are `1200` and `18000`. They use positive-integer fields with no invented unit or maximum; the UI does not claim a precise distance or guaranteed performance effect. The pair must satisfy `Length >= MinLength`. Existing incomplete or invalid pairs are preserved and shown as unconfigured/invalid; saving requires a valid pair or an explicit application of the recommended values. The pair's reset action removes both properties together.

The image-quality and anti-aliasing properties added under `[SystemSettings]` are absent from the clean baseline. Their recommended values are `r.FilmGrain=0`, `r.FilmGrainIntensity=0`, `r.SceneColorFringeQuality=0`, `r.Tonemapper.Quality=0`, `r.PostProcessQuality=0`, `r.DOF.Gather.EnableBokehSettings=0`, `r.Tonemapper.Sharpen=0`, `r.DefaultFeature.AntiAliasing=0`, `r.TemporalAA.Upsampling=0`, `r.TemporalAA.Algorithm=0`, and `r.TemporalAA.FilterSize=0`. Boolean properties use switches; `r.DefaultFeature.AntiAliasing` is an integer field that preserves the raw value rather than mapping it to unconfirmed method labels; other values use integer or decimal fields appropriate to their supplied form. The community-supplied `r.PostProcessQuality` key is retained as given rather than silently replaced by `sg.PostProcessQuality`. These settings remain independent of the DLSS/FSR selector; player-facing explanations describe their intended effects directly. `r.PostProcessAAQuality` is managed in the Post-processing category below.

The distance, LOD, and streaming properties added under `[SystemSettings]` are absent from the clean baseline. Their recommended values are `r.ViewDistanceScale=3`, `r.SkeletalMeshLODBias=1`, `r.StaticMeshLODDistanceScale=10`, `r.ParticleLODBias=1`, `r.Streaming.PoolSize=0`, `r.Streaming.LimitPoolSizeToVRAM=1`, `r.Streaming.DefragDynamicBounds=1`, and `r.Streaming.FramesForFullUpdate=5`. Boolean properties use switches; view-distance and static-mesh scale properties use decimal fields; LOD biases, pool size, and frame count use integer fields. No arbitrary numeric maximum is imposed where a supported range is not established. Player-facing explanations describe `r.Streaming.PoolSize=0` as unlimited on its own, `LimitPoolSizeToVRAM=1` as requesting a VRAM-based limit, `DefragDynamicBounds` as removing unused dynamic bounds from the streaming update loop, and `FramesForFullUpdate` as distributing full streaming updates across frames. Visible warnings call out the potential load increase from greater view distance, reduced LOD detail, and streaming/VRAM tradeoffs before applying the profile. Version and integration uncertainties remain in this ADR only.

The frame-latency properties `r.OneFrameThreadLag` and `r.FinishCurrentFrame` are absent from the clean baseline and both have recommended value `1`. They use independent boolean switches. Their explanations state that the first permits up to one frame of thread lead/lag for pipelining, while the second forces the current frame to finish and render rather than remain buffered, potentially lowering latency at a performance cost. The UI does not claim they cancel or exclude one another; a visible warning before application describes the latency/performance tradeoff of enabling both.

The post-processing properties added under `[SystemSettings]` are absent from the clean baseline. Their recommended values are `r.PostProcessAAQuality=0`, `r.ScreenPercentage=100`, `r.Tonemapper.GrainQuantization=0`, `r.LensFlareQuality=0`, `r.BloomQuality=0`, `r.MotionBlurQuality=0`, `r.DepthOfFieldQuality=0`, `r.SSR.Quality=0`, `r.SSAO=0`, `r.AmbientOcclusionLevels=1`, `r.SSS.Scale=0`, and `r.SSS.SampleSet=0`. Quality CVars use selectors based on documented Unreal levels rather than unrestricted numeric fields; `r.ScreenPercentage` uses a numeric percentage field. Player-facing explanations describe `r.ScreenPercentage=100` as the output-resolution scale and do not conflate it with DLSS quality; `r.Tonemapper.GrainQuantization` is distinguished from the film-grain controls in the image-quality category as tonemapper quantization noise. The AO settings remain independent: `r.AmbientOcclusionLevels=1` means one level, not AO disabled, and `r.AOQuality` from the shadow category concerns distance-field AO. The two SSS properties remain separately editable even though `r.SSS.Scale=0` can make the sample-set choice visually inactive. The category-level recommended action applies these 12 values to this category only; otherwise absent values remain unconfigured and are not written until explicitly selected. Uncertainties about `r.SSAO` and engine integration remain internal to this ADR.

For `[/Script/Engine.GarbageCollectionSettings]`, `TimeBetweenPurgingPendingKillObjects` is absent from the clean baseline and has recommended value `30`. It is manually editable as a positive decimal number of seconds, with no arbitrary upper bound. The player-facing explanation describes the intended purge interval and notes that shorter or longer intervals can change garbage-collection behavior without promising a direct FPS improvement. The version caveat remains internal to this ADR; preserve the community-provided key and section as supplied.

The UI/texture/VRAM properties are absent from the clean baseline and are kept in the community-provided `[UI]` section. Their recommended values are `r.Streaming.MipBias=0`, `r.Streaming.UseAllMips=1`, `MinTextureResidentMipCount=16`, `MaxTextureSize=0`, and `PoolSizeVRAMPercentage=95`. `r.Streaming.MipBias` uses a decimal numeric field, `r.Streaming.UseAllMips` a switch, and the remaining three use integer fields; `PoolSizeVRAMPercentage` is labeled as a percentage. No unsupported validation bounds are imposed. Player-facing explanations describe MipBias 0 as no global mip bias and UseAllMips as allowing all available mip levels, alongside a warning that doing so can increase VRAM pressure. Explanations for the other properties use the intended effects supplied by the player. Section/key compatibility uncertainties remain internal to this ADR; preserve the supplied section and keys exactly under the community-settings policy.

The shader compilation and pipeline-cache properties are absent from the clean baseline and are kept in the community-provided `[Character]` section. Their recommended values are `r.CompileShadersForDevelopment=False`, `r.ShaderPipelineCache.Enabled=1`, `r.ShaderPipelineCache.StartupMode=3`, `r.ShaderPipelineCache.GameFileMaskEnabled=1`, `r.ShaderPipelineCache.BackgroundBatchingTime=-1`, and `r.XGEShaderCompile=1`. Boolean entries use switches; `StartupMode` uses a selector for `0 Paused`, `1 Fast`, `2 Background`, and `3 Precompile`; `BackgroundBatchingTime` uses a signed numeric field that accepts `-1` without an invented range. Player-facing explanations describe the intended compilation/cache behavior and the startup mode, without warnings that the client may not support the settings. These properties remain editable and included in the recommended profile. Official-source limitations and uncertainty about the exact semantics of `BackgroundBatchingTime=-1`, packaged-client behavior, and Aion 2's handling remain internal to this ADR.

Engine.ini keys and sections supplied by the player from community recommendations are treated as functional as provided, without requiring official Unreal documentation to confirm their Aion 2 behavior.

On Windows, the native-resolution query matches the chosen monitor’s GDI name to an active CCD display path and reads its preferred target mode through [DisplayConfigGetDeviceInfo](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-displayconfiggetdeviceinfo) and [DISPLAYCONFIG_TARGET_PREFERRED_MODE](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/ns-wingdi-displayconfig_target_preferred_mode). If the preferred mode cannot be determined, the suggestion is unavailable rather than substituting the desktop resolution. On Linux, the preferred mode is obtained from xrandr. No display configuration is changed by these queries.
