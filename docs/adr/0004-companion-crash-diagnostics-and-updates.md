# Companion for crash diagnostics and updates

Status: accepted; installer-managed updates amended on 11 November 2026.

For installer-managed Windows installations, distribution, update permissions,
channel scope, personal-data migration and service coordination are amended by
[ADR 0007](0007-windows-installer-and-update-service.md).

Aetheris uses a separate companion process as its normal entry point. The companion starts before the application, launches and monitors it, and remains available when startup fails or the application crashes. A direct launch of the application executable starts the companion and delegates the application launch to it. The companion uses a simple interface and dependencies independent of GPUI so it can report failures when the main interface cannot start. This makes diagnostics available even when the GPUI window never opens and allows the application executable to be updated while it is stopped. The first implementation targets Windows; the architecture should remain adaptable to Linux. A failure that prevents the companion itself from starting cannot be reported by that companion.

On a normal user-initiated application shutdown, the companion also exits. On a crash or startup failure, it stays open, displays the diagnostic information available and the log location, and offers to open the log directly in the associated editor, restart the application, or close the companion. Opening the log keeps the diagnostic open and never restarts the application. A further crash after a user-requested restart is displayed and requires another user action, with no automatic restart loop. It must not invent a cause when only a process exit code or incomplete information is available. An exit without an explicit normal-shutdown signal is treated as unexpected, including an application process forcibly terminated by the user. Logs remain local and are shared only by an explicit user action; they include available application and Windows versions, startup progress, errors, and process exit status. The ten most recent launch logs are retained; older logs are removed.

The companion obtains new versions from the public GitHub Releases of `Ayato-san/Aetheris`. Stable releases are the default; Aetheris also offers one prerelease channel, whose releases may be called beta, candidate, nightly, or canary. This channel also receives newer stable releases. For now, the installed application version is displayed at the bottom of the sidebar; clicking it opens the channel selector above that value, with the current channel marked. Choosing a channel, clicking outside the selector, or pressing Escape closes it. This selector will move to the settings page when that page exists. The displayed version is prefixed with `v`; beta versions are shown as `v1.2.3-beta-2`, while release tags and version comparisons retain standard SemVer such as `1.2.3-beta.2`. Each release has a comparable version number to prevent an unintended downgrade. Switching back to stable does not automatically downgrade an installed prerelease; the application stays on its current version until a newer eligible stable release is available. Release packages carry an Ed25519-signed manifest binding the SemVer version, target platform, and SHA-256 hashes of all distributed program files. They are signature-verified before installation; missing or invalid signatures cause the update to be refused. The public verification key is supplied at compilation and embedded in the companion and the other programs; the private signing key is kept outside the repository and is available only to the signing step of publication. At every companion startup, the installed application binaries are checked against authenticated release information to detect local modifications, and the installed version is compared with the latest eligible version on the selected channel.

The ZIP includes signed verification information, so installed files can be checked offline. The check covers distributed program files, including the companion and its update helper, but excludes user settings and logs. Modified or corrupted program files block application launch and prompt the user to repair the installation from a signed release while preserving personal data. Repair preferentially reinstalls the same signed version. If that version is unavailable or its identity cannot be authenticated, the companion offers the latest signed version of the selected channel, with explicit confirmation because the version may change. Missing or unauthenticatable verification information also blocks launch and offers repair, with a distinct message that integrity could not be established. If repair is impossible offline, the companion remains open with an error and a retry action; application launch stays blocked. The companion's self-check cannot establish trust in an already modified companion on its own. Offline operation can verify local integrity but cannot determine whether a newer release exists. Production builds always require an authenticated manifest and a configured public key. Debug builds without a manifest may run unsigned for local development and do not perform the automatic startup update check; this exception does not establish release integrity.

The application opens without waiting for the startup update check. An update found within three seconds of launch may be downloaded and verified in the background while the application is open, then installed automatically after the application has closed normally. If the user interacts with Aetheris before the update is ready, automatic closure is cancelled and installation waits for the user's action. A normal user-initiated closure during that download cancels it and closes the companion. A result arriving after the three-second limit is announced in the application and waits for the user's update action. The companion also checks for updates hourly during use, but does not download their packages until the user clicks the update button, so background downloads do not interfere with network use. A user-requested download likewise runs while the application remains open; once the package has been verified, the application closes normally and the companion performs the update. If the application cannot close, for example because pending input cannot be saved, the update waits. After a successful update, the companion automatically relaunches the application. If the release service is unreachable or an update fails, the previous version remains available to launch and the problem is reported. If the updated application crashes on its first launch before its main window has remained open for ten seconds, the companion offers to restore the previous version; a normal user-initiated closure during this interval is not a crash. After restoration, the failed version is excluded from automatic reinstallation. An installation failure also excludes that version from automatic retry to avoid a relaunch/update failure loop; the user may retry it, and newer versions remain eligible. Updates and recovery preserve user settings, logs, and other personal data, including existing files such as `Engine.baseline.ini` beside the executables. Data affected by a migration is backed up before modification so it can be restored with the previous version. Before restoring that backup, the companion preserves a separate copy of the post-crash data and explains that the older backup will become active. For manual ZIP installations, if the installation directory is not writable, the companion reports the problem and leaves the previous version usable without automatically requesting administrator privileges.

Windows x86-64 MSVC releases provide an Inno Setup installer as the primary download and retain a ZIP containing the companion, application, and update helper executables, plus `release.json` and `release.sig`. The installer-managed update path and its privilege boundary follow [ADR 0007](0007-windows-installer-and-update-service.md); writable manual ZIP installations continue to use the temporary helper directly. Existing unsigned builds require a one-time manual move to the new signed ZIP, preserving personal files. Releases must also be able to update the companion itself: a temporary helper replaces the stopped companion executable and relaunches the updated companion. The distribution repository is `Ayato-san/Aetheris`; the manual stable and beta publication workflows are included in the repository. GitHub-based distribution still requires configuring the `release` environment with the public-key variable `AETHERIS_PUBLIC_KEY`, the private-key secret `AETHERIS_SIGNING_KEY`, and the permissions needed to push release commits and tags and publish releases. The repository and release downloads are intended to be public; access restrictions can be considered later.

SQLite schema changes are reconciled incrementally during updates: each database records its applied migrations, and every missing migration is applied in order, even when intermediate application releases are skipped. For example, updating from 1.0.1 to 1.1.3 applies the migrations introduced in 1.1.1, 1.1.2 and 1.1.3 in sequence; updating from 1.1.2 to 1.1.3 applies only the 1.1.3 migration. Releases must retain the necessary migration history for these update paths. A fresh installation creates the current schema directly and records the corresponding migration state.

For direct ZIP updates, reconciliation runs in SQLite transactions alongside the update. After migrations succeed and the new program files are installed, the transactions are committed before the new application is launched. On migration or installation failure, uncommitted transactions are rolled back, the previous application and all affected databases are restored, and the error is logged and displayed. Because SQLite transactions do not atomically include executable replacement or necessarily coordinate separate databases, the updater retains consistent backups and durable recovery state. Each program file is copied to a separate temporary file, flushed, and replaced atomically, so an interruption during replacement leaves a complete old or new companion available to start recovery; if the companion or machine stops during the operation, the next launch detects the interruption and restores the previous application and all affected databases together. A first-launch crash after commit uses the previously described backup restoration flow.

Two manually triggered GitHub Actions workflows build, sign and publish Windows releases from the main branch, producing both the signed ZIP and the installer before publication. Both accept a major.minor.patch version. The stable workflow publishes that version; the beta workflow publishes standard SemVer prereleases such as `1.2.3-beta.1` and `1.2.3-beta.2`. For each major.minor.patch combination, the beta counter starts at 1 and is derived from the existing beta tags; concurrent publications must not select the same number. Both workflows update the version in `Cargo.toml` and `Cargo.lock` and create a commit and tag corresponding to the release, using the repository's Conventional Commit policy. Compilation, project checks, and signing must succeed before publishing; a failure must not produce an incomplete release. The signing private key is kept out of the repository and protected in the publication system.

One Aetheris instance runs per user profile. A repeated launch activates the existing window. Installer-managed updates coordinate every active instance across Windows sessions through shared installation leases and an exclusive update lease. The GUI retains its own installation lease so a companion crash cannot permit replacement while the GUI is still running.

A released cooperative lease does not prove that Windows has unloaded the companion or application image. Before replacing programs, the helper also waits for real executable users under [ADR 0007](0007-windows-installer-and-update-service.md). A launch attempted during an update activates the existing progress window and exits promptly; neither the application nor the companion opens a blocking dialog from an executable awaiting replacement. A supervised application child may finish starting while an update is queued because its companion already holds the installation lease. This preserves the normal close-and-handoff protocol instead of introducing a false startup crash.

Managed services never migrate personal databases as SYSTEM. Each owner reconciles their database on access, with schema backups and preservation of post-update data on rollback. Direct ZIP updates retain the existing transaction-and-backup migration flow described above.

## Implementation and distribution readiness

The companion, native Windows diagnostics, authenticated loopback protocol, signed-package tooling, integrity checks, update and repair flows, durable recovery, SQLite migration history, sidebar channel selector, and release workflows are implemented. The application and companion have been compiled and checked on Windows; local tests cover signatures, version selection, migration rollback, interrupted installation, and restoration with preservation of post-crash data. Graphical Windows checks also exercised startup, normal shutdown, and opening a local log from a simulated crash without restarting the application.

Local compilation and tests do not establish complete installer and service behavior on a clean Windows machine. End-to-end checks still include signed-package update and recovery, repairs, separate administrator credentials and concurrent Windows sessions. Operational instructions and the remaining publication checks are maintained in [the release guide](../releases.md).
